## איך זה בנוי

```
מסלול אישורי ההגעה (rsvp_timeline / communication / rsvp_scheduler)  ← לא יודע כלום על Meta
        ↓
outbound.send_batch            — רושם לפני שליחה, מעדכן אחרי, נעילה לאירוע, סינון meta_test
        ↓
messaging.get_provider()       — Mock / TestRecipientGuard(Meta) / Meta / Stopped
        ↓
Meta Cloud API

Meta webhook → /messaging/webhook → whatsapp_inbound (שיוך) + message_status (מסירה)
```

| קובץ | אחריות |
|---|---|
| `backend/app/messaging.py` | מצב השליחה, בחירת הספק, רשימת הנמענים המורשים |
| `backend/app/outbound.py` | כל שליחה יוצאת: רישום `pending` → שליחה → עדכון |
| `backend/app/message_status.py` | אוצר המילים של הסטטוסים, עדכוני מסירה מ-webhook |
| `backend/app/whatsapp_inbound.py` | שיוך תשובה נכנסת למוזמן — רק התאמה חד-משמעית |
| `backend/app/routers/messaging.py` | ה-webhook (אימות חתימה, עיבוד פריט-פריט) |

## מצבי שליחה — `WHATSAPP_MODE`

| ערך | מה קורה |
|---|---|
| `mock` (ברירת מחדל) | שום הודעה לא יוצאת. נרשמת ביומן כ"נשלחה" לצורך בדיקת הזרימה |
| `meta_test` | שליחה אמיתית דרך Meta **רק** לטלפונים שב-`WHATSAPP_TEST_RECIPIENTS` |
| `meta` (או `live`, הכינוי הוותיק) | שליחה אמיתית לכל המוזמנים. **רק באישור מפורש של המייסד** |
| חסר / ריק / לא מוכר | `mock` (ערך לא מוכר נרשם בלוג כאזהרה) |

עצירת חירום מהאדמין (`whatsapp.emergency_stop`) גוברת על כל מצב.

המסכים מקבלים `mock` / `meta_test` / `live` (גם `meta` מוצג כ-`live`, כמו שהיה).

### `meta_test` — למה הוא בטוח גם מול מסד הייצור

- **רשימה מורשית:** `WHATSAPP_TEST_RECIPIENTS` — טלפונים מופרדים בפסיק, נקודה-פסיק
  או שורה חדשה, בכל פורמט ישראלי (`050-1234567`, `972501234567`, `+972 50 123 4567`).
  רשומה פגומה מדולגת. רשימה חסרה או ריקה = **הכול חסום**.
- **נמען לא מורשה נחסם לפני Meta ובלי שורה במסד.** `send_batch` מסנן אותו עוד לפני
  הרישום — הוא לא מקבל "נכשלה" שהייתה סוגרת לו את הסבב, ושום נתון שלו לא משתנה.
- **שכבה שנייה:** הספק עצמו (`TestRecipientGuard`) בודק שוב בכל שליחה — גם במסלולים
  שלא עוברים דרך `send_batch`, כמו "שליחת בדיקה" לטלפון של בעלי האירוע.
- **המשימה המתוזמנת** לא כותבת שורת יומן כשהכול נחסם (כדי לא למלא יומן כל 15 דקות).
- **שני ה-endpoints הישנים** `/messaging/invitations/send` ו-`/messaging/reminders/send`
  (בלי כפתור במסכים, בלי מניעת כפילויות) מחזירים `409` בכל מצב שאינו `mock`.

## הודעות שנתקעו ב-`pending`

### מה זה
כל הודעה נרשמת במסד בסטטוס `pending` לפני שהיא נשלחת, ומתעדכנת מיד אחרי
(`sent` / `failed`). אם השרת נופל בין השליחה לעדכון, השורה נשארת `pending` —
ייתכן ש-Meta קיבלה את ההודעה, וייתכן שלא.

### מה המערכת עושה היום
- **אף מסלול אוטומטי לא שולח אותה שוב.** המשימה המתוזמנת והשליחה מהתור מדלגות
  על כל מוזמן שיש לו שורה לאותו סבב, בכל סטטוס. שליחת הזמנות של בעלי האירוע
  ("חדשים", "כולם", "ניסיון חוזר", מוזמן ספציפי) מתייחסת ל-`pending` כ"אולי נשלחה".
  (בדיקות: `test_whatsapp_safety.py` — B2, E3.)
- **רק אדמין-על** יכול לשלוח שוב, כפעולה ידנית ומכוונת ("שלח לכולם").
- **במסך המעקב** של בעלי האירוע הודעה כזו נספרת היום יחד עם "ממתינים לשליחה".
- **במצב `mock`** הודעה נתקעת רק אם השרת נפל באמצע שליחה.

### איך מוצאים אותן היום (שאילתה, קריאה בלבד)
```sql
SELECT id, event_id, guest_id, kind, created_at
FROM messages
WHERE direction = 'outbound' AND status = 'pending'
  AND created_at < now() - interval '15 minutes'
ORDER BY created_at;
```

### הפתרון המתוכנן (לא נבנה — דורש אישור)
1. **השלמה אוטומטית (שלב 3):** כל הודעה תישלח ל-Meta עם המזהה הפנימי שלנו. אם Meta
   קיבלה אותה, עדכון הסטטוס יגיע עם המזהה הזה ויסגור את השורה. לבדוק מול התיעוד של
   Meta שהשדה אכן חוזר ב-webhook לפני שסומכים עליו.
2. **רשימה באדמין:** "הודעות במצב לא ידוע" — רק מה שלא נסגר אחרי 24 שעות, עם פעולה
   אחת: "סמן כלא נשלחה". הפעולה לא שולחת דבר; היא רק פותחת את הניסיון החוזר הרגיל.
3. **מסך המעקב:** להציג הודעה כזו כ"בבדיקה" ולא כ"ממתינה לשליחה".
