# UX Writing — הטקסטים בתוך המערכת

**מקור האמת: `frontend/src/strings/he.ts`.** הקובץ הזה מסביר איך כותבים.
טקסט חדש נכנס ל-`he.ts` — אף פעם לא ישירות לתוך קומפוננטה.

---

## 1. כפתורים

**שם פועל, 1–3 מילים, אומר מה יקרה.**

```
✓ שמירה · ביטול · הוספת מוזמן · עריכת פרטים · שליחת תזכורת · העלאת רשימה
✗ שמור · אישור · OK · המשך · שלח · לחץ כאן
```

**הכפתור אומר את הפעולה, לא את ההסכמה:**
```
✗ [ אישור ]  [ ביטול ]        ← "אישור" של מה?
✓ [ שליחה למוזמנים ]  [ ביטול ]
```

**בדיאלוג הרסני — הכפתור חוזר על הפעולה:**
```
"להסיר את דנה מהרשימה?"
[ הסרה ]   [ ביטול ]
```

---

## 2. כותרות מסך

עד 6 מילים. שם המקום, לא תיאור שלו.

```
✓ "המוזמנים שלכם" · "מפת האולם" · "סידור ההושבה" · "אישורי הגעה"
✗ "ניהול רשימת המוזמנים במערכת" · "מסך הושבה"
```

---

## 3. מצבים ריקים — הכי חשוב במוצר

מצב ריק הוא **הרגע שבו משתמש חדש מחליט אם להישאר**. הוא לא דיווח על ריקנות —
הוא הזמנה לפעולה.

**מבנה: מה יהיה כאן + למה זה שווה + כפתור אחד.**

```
✓ "עדיין אין מוזמנים — בואו נוסיף את הראשונים"
   [ הוספת מוזמן ]   [ העלאת רשימה מאקסל ]

✓ "השולחנות עוד ריקים. אפשר לשבץ ידנית, או לתת ל-VEYA להציע סידור"
   [ מילוי חכם ]

✗ "לא נמצאו מוזמנים"  ·  "אין נתונים להצגה"  ·  "הרשימה ריקה"
```

**מצב ריק אחרי סינון** — שונה ממצב ריק אמיתי:
```
✓ "אין מוזמנים שמתאימים לסינון הזה"  [ ניקוי הסינון ]
```

---

## 4. הודעות שגיאה

**נוסחה: מה קרה (בלי להאשים) + מה עושים עכשיו.**

```
✓ "לא הצלחנו לטעון כרגע. ננסה שוב"
✓ "לא הצלחנו לשמור את הפרטים. נסו שוב"
✓ "נראה שהמספר לא תקין — בואו נבדוק אותו שוב"
✓ "התמונה גדולה מדי — עד 3MB"
✓ "אפשר להעלות קובץ תמונה בלבד"

✗ "אירעה שגיאה" · "מספר טלפון שגוי" · "קלט לא חוקי" · "הפעולה נכשלה"
✗ "Error 500" · "שגיאת שרת"
```

**שלושה סוגים, שלושה טיפולים:**

| סוג | דוגמה | הכלל |
|---|---|---|
| **אשמת המערכת** | נפילת רשת, שרת | "לא הצלחנו…" + ננסה שוב. **אף פעם לא מתנצלים ארוכות** |
| **קלט לא תקין** | טלפון, מייל | "נראה ש…" + מה מצופה. אף פעם "שגוי" |
| **פעולה חסומה** | הרשאה, נעילה | להסביר **למה** נחסם, לא רק שנחסם |

**הכלל שהכי קל להפר:** שגיאה בלי צעד הבא היא לא הודעת שגיאה, היא תלונה.

---

## 5. הודעות הצלחה

**קצר. עובדתי. בלי חגיגה.**

```
✓ "נשמח"  →  לא. ✓ "נשמר"
✓ "12 מוזמנים נוספו"
✓ "התזכורת נשלחה ל-45 מוזמנים"

✗ "מעולה! הפרטים נשמרו בהצלחה! 🎉"
✗ "הפעולה בוצעה בהצלחה"
```

מספרים בהודעת הצלחה = ביטחון. "נשלח" פחות טוב מ-"נשלח ל-45 מוזמנים".

---

## 6. טקסט עזר והסברים

משפט אחד. עונה על "למה זה חשוב לי", לא "מה זה".

```
✓ commitExplain: "כמה ימים לפני האירוע צריך למסור לאולם מספר סופי?
   ביום הזה כל אישורי ההגעה נסגרים, ולוח הזמנים שלהם נבנה לאחור סביבו."
✓ "זו התמונה שתישלח למוזמנים בהזמנה"

✗ "שדה זה מגדיר את מספר הימים לפני האירוע"
```

**הסבר טוב עונה על שאלה שהמשתמש שאל בראש.** אם אף אחד לא היה שואל — מחק.

---

## 7. Onboarding לזוג חדש

**עיקרון: לא מסבירים את המערכת. מתקדמים באירוע.**

כל שלב = הישג אמיתי, לא צעד בטופס:

```
1. "בואו נתחיל מהאירוע"        ← סוג, תאריך, מקום
2. "מי מגיע?"                   ← הוספה ראשונה / העלאת אקסל
3. "מתי שולחים?"                ← מועד סגירת הרשימה → לוח זמנים אוטומטי
```

**כללי onboarding:**
- **אף פעם לא "סיור במערכת".** משתמש רוצה לסיים משימה, לא ללמוד תוכנה.
- **תמיד אפשר לדלג**, ותמיד ברור מה מפסידים.
- **המסך הראשון אחרי ההרשמה מראה התקדמות**, לא מסך ריק.
- מותר משפט אחד של הרגעה בהתחלה: "אפשר לשנות הכול אחר כך."

---

## 8. ניהול מוזמנים

המסך הכי נצפה במערכת. השפה שם צריכה להיות **הכי יבשה והכי מדויקת**.

| מצב | הטקסט |
|---|---|
| אישרו | "אישרו הגעה" |
| לא מגיעים | "לא מגיעים" (לא "סירבו") |
| ממתינים | "ממתינים לתשובה" (לא "לא ענו") |
| אולי | "לא החליטו" |

**סיכומים** — מספר + הקשר: `"87 אישרו הגעה מתוך 240"`.

**ייבוא** — הרגע הכי מלחיץ בכל המוצר. משתמש מעלה קובץ ולא יודע מה יקרה:
```
✓ "מצאנו 187 מוזמנים בקובץ. 4 שורות דורשות תשומת לב"
   [ סקירת ה-4 ]   [ ייבוא הכול ]
✗ "הייבוא הושלם עם 4 שגיאות"
```

---

## 9. סידורי הושבה

הפיצ'ר הכי "AI" — ולכן הכי צריך **שפה שמורידה חשש ומחזירה שליטה**.

**הכלל:** VEYA **מציעה**, בעלי האירוע **מחליטים**. אף פעם לא "המערכת קבעה".

```
✓ "הצענו סידור לכל המוזמנים שאישרו. אפשר לשנות כל שולחן"
✓ "מילוי חכם"
✓ "3 מוזמנים עדיין בלי שולחן"
✓ "שמנו את משפחת כהן יחד, לפי מה שסימנתם"

✗ "האלגוריתם שיבץ 240 מוזמנים"
✗ "אופטימיזציה הושלמה"
✗ "המערכת קבעה את הסידור הטוב ביותר"
```

**אזהרות רכות — מזהירות, לא חוסמות:**
```
✓ "שולחן 7 מלא. אפשר להוסיף בכל זאת"
✗ "חריגה מקיבולת השולחן!"
```

**מגבלות שהמשתמש הגדיר** — לשקף בשפה שלו:
```
✓ "דנה ואיתי לא יושבים יחד — כמו שביקשתם"
```

## 10. פערי כיסוי ב-`he.ts` (נכון ל-2026-07-24)

`he.ts` מכסה היום **3 מקטעים בלבד**: `common`, `dashboard`, `guests`.
16 מתוך ~35 קומפוננטות מייבאות אותו.

**חסר — לפי סדר עדיפות:**

| מקטע | מה כולל | עדיפות |
|---|---|---|
| `errors` | שגיאות משותפות לכל המערכת | גבוהה — הכי הרבה כפילות |
| `seating` | סידור הושבה, מילוי חכם, אזהרות | גבוהה — הכי חשוף ל-AI |
| `hall` | עורך מפת האולם | גבוהה |
| `rsvp` | מסך אישור ההגעה (מה שהמוזמן רואה) | גבוהה — פנים החוצה |
| `import` | ייבוא אקסל, הדבקה, אנשי קשר | בינונית |
| `onboarding` | פתיחת אירוע ראשון | בינונית |
| `messages` | מסך שליחת הודעות ואוטומציות | בינונית |
| `profile` · `legal` | פרופיל, קוקיז, הסכמות | נמוכה |

זו רשימת העבודה לשלב 4 בתוכנית.
